# Memory in the LLM Era: Modular Architectures and Strategies in a Unified Framework [Experiment, Analysis & Benchmark]

- **Authors / venue / year:** Wu, Lin, Zhou, Zhang, Guo, Zhou, Wang, Liu, Ma, Fang (CUHK-Shenzhen / CUHK / HITSZ / BIT / Huawei Cloud) — PVLDB Vol. 19, 2026.
- **arXiv / DOI:** arXiv:2604.01707v2 [cs.CL]
- **Source:** folder (`Memory in the LLM Era, Modular Architectures and Strategies in a Unified Framework.pdf`)
- **Overall relevance to longmem-npc:** High — it is an apples-to-apples empirical comparison of 10 memory systems (A-MEM, MemoryBank, MemGPT, Mem0, Mem0g, MemoChat, Zep, MemTree, MemoryOS, MemOS) on LOCOMO + LongMemEval, and several of its measured effects (destructive-update fragility, conflict-density degradation, connecting-operator payoff) directly validate or challenge specific components in our baseline.
- **Core contribution (2-3 sentences):** Proposes a unified 4-stage framework (Information Extraction → Memory Management → Memory Storage → Information Retrieval) that every surveyed system is decomposed into, then benchmarks 10 reimplemented systems under identical settings on LOCOMO and LongMemEval, analyzing token cost, context scalability, evidence-position sensitivity, and backbone dependence. It closes by combining the best-performing modules (tree/hierarchical storage + heat-based tier promotion) into a new method that beats all 10 baselines at a fraction of the token cost.

### Mechanisms relevant to us
- **Memory Management taxonomy** (§5): Connecting, Integrating, Transforming, Updating, Filtering — a checklist against which our write/decay/correction pipeline can be placed. We do Updating (correction verbs) and a form of Transforming (reconstruction's write-back), but nothing for **Connecting** (no associative/graph links between memories) or explicit **Integrating** (no consolidation of fragments into higher-level summaries).
- **Retrieval paradigm taxonomy** (§7): Lexical-Based (BM25/Jaccard), Vector-Based, Structure-Based (graph traversal/multi-hop), LLM-Assisted (LLM decides/reformulates what to retrieve). Our read path (`app\retrieval.py`) is pure Vector-Based only.
- **Filtering/forgetting** (§5, "Filtering Obsolete Information"): usage-based (access frequency + time decay, e.g. MemoryOS/MemoryBank) vs. content-based (semantic dedup via LLM). Our decay (`app\decay.py`) is time+importance only — no usage/access-frequency term.
- **Updating paradigms** (Table 2): rule-based / LLM-based / agent-based. Our correction verbs are rule-based-plus-one-embed-call; nothing autonomous (no system-initiated conflict detection).
- **Experimental finding — hierarchy wins:** "Tree-based memory methods (e.g., MemTree and MemOS) generally achieve strong performance by organizing memory in a multi-layered, multi-granularity fashion" (§8.2 Exp.1) — direct evidence for the baseline's noted gap "No hierarchical/schema memory."
- **Experimental finding — connecting matters for multi-hop:** "Methods lacking such associative operations, such as MemoryBank, MemGPT, and MemoChat, perform poorly on the Multi-Session tasks of LONGMEMEVAL and the Multi-Hop tasks of LOCOMO" (§8.2 Exp.1(3)) — direct evidence for the baseline's noted gap "No graph / associative structure over memories... No multi-hop retrieval."
- **Experimental finding — conflict density degrades retrieval:** "Knowledge Update (KU) is particularly sensitive [to context scaling], showing sharp performance attrition because an increased memory volume raises the density of conflicting records... the presence of more obsolete candidates directly increases retrieval interference" (§8.2 Exp.3(3)) — this validates our one-live-head partial-index design (`memory_fact_versions`, migration 002): only the live fact head is ever a retrieval candidate, so obsolete versions can never compete as noise.
- **Experimental finding — destructive update hurts position robustness:** "For methods like A-MEM, dynamic memory revisions can overwrite earlier evidence, making early-session information vulnerable to later interactions" (§8.2 Exp.4(2)) — a measured failure mode of destructive/in-place memory rewriting, which our non-destructive bi-temporal invariant avoids by construction.
- **Lesson L5** (§9, Appendix D): "Instead of destructive updates, memory systems should adopt non-destructive strategies that preserve historical information while annotating its validity... instead of deleting old information, systems should keep it and mark its status." This is the paper's own practitioner lesson, and it is verbatim our invariant #1.
- **Opportunity O3** (§9): "Existing hierarchical memory mechanisms primarily focus on consolidating short-term memory into long-term storage but do not support the reverse transformation. A promising direction is to design bidirectional memory transformation mechanisms that enable efficient consolidation and reconstruction across memory hierarchies." — the paper names, as an open future-work item, essentially what our reconstruction mechanism (`app\reconstruction.py`) already does: long-term compressed/gist content re-expanded ("retold") on demand with a bounded drift check. Worth using in positioning writeups.

### STRICTLY-BETTER candidates (beats a mechanism we already have)

- **Component touched:** Read path / retrieval (`app\retrieval.py`, `docs\read-path.md`) — the vector-only candidate query.
- **Our current mechanism:** `query_text` is embedded as-is and matched purely by cosine distance against the live fact head's HNSW index (2026-07-14 ruling: server-side query composition explicitly rejected as double-counting).
- **Paper's mechanism:** Hybrid retrieval combining lexical (BM25/Jaccard) and vector signals — evidence §7, "Lexical-based retrieval provides a strong baseline for exact term matching, which can be particularly effective for retrieving names, specific entities, or phrases where precise wording is critical," contrasted with vector retrieval's strength at "latent semantic nuances."
- **Why strictly better:** NPC dialogue queries frequently contain proper names (other characters, places, items) where exact lexical match is more reliable than embedding cosine similarity, which can conflate similar-sounding or semantically-adjacent names. A hybrid score (or a lexical pre-filter unioned into the ANN candidate set) would improve recall on exactly this class of query without touching the existing relevance/recency/importance scoring formula.
- **Adoption cost/risk in our stack:** Postgres has native full-text search (`tsvector`/`GIN`) that could sit alongside the existing HNSW index on `memory_fact_versions`, hand-written SQL, no ORM — a plausible fit. Would need a new fusion-weight knob (integrator-configurable per invariant #5) and a migration for the text-search index. Moderate scope, not a redesign.
- **Docs it would touch:** `docs\read-path.md`, `architecture.md` §6.
- **Confidence:** Medium (the general lexical/semantic complementarity claim is well-evidenced across IR literature and repeated in this paper's taxonomy; it is not benchmarked by this paper as an ablation against pure-vector on LOCOMO/LongMemEval specifically).

*(No second strictly-better candidate found with concrete evidence in this paper beyond the above — its other measured advantages, e.g. hierarchical storage and connecting operators, are capabilities we entirely lack today rather than refinements of an existing mechanism, so they are filed as NOT-YET-BUILT below.)*

### NOT-YET-BUILT candidates (a capability we simply don't have)

- **Capability:** Connecting Related Experiences — associative links or graph edges between memory entries (semantic similarity, temporal proximity, contextual relevance).
- **What the paper does:** A-MEM and MemoryOS build associative links for "synchronous updates and alignment across connected memories"; Zep and Mem0 build structural graph edges between episode/entity nodes — evidence §5, "Connecting," and Table 2. Directly measured payoff: connecting-operator methods win Multi-Hop/Multi-Session tasks (§8.2 Exp.1(3), quoted above).
- **Why worth adopting for an NPC memory service:** Baseline explicitly flags "No graph / associative structure over memories (no entity graph, no linking beyond identity-components + gist spans + entities[]). No multi-hop retrieval." An NPC answering "why does she still trust me after that?" needs to chain across two or three separate memories, which flat top-k vector retrieval structurally cannot do.
- **Adoption cost/risk in our stack:** A genuinely new schema surface (an edges table or a lightweight property-graph layer over `memories`/`memory_fact_versions`), plus a retrieval-time traversal step. Real build scope — its own migration and its own spec session, not a bolt-on. Compatible with non-destructive storage (edges can themselves be bi-temporal rows).
- **Docs it would touch:** New `docs\` spec (e.g. `docs\memory-graph.md`), `architecture.md` §6, `migration-01.md`-style ledger entry.
- **Confidence:** High (capability gap is explicit in our own baseline; payoff is directly measured in this paper).

- **Capability:** Hierarchical/tiered memory storage with usage-weighted promotion (short-term → mid-term → long-term).
- **What the paper does:** MemoryOS's three-tier hierarchy (FIFO short-term → topic-segment mid-term → heat-scored long-term) and the paper's own new SOTA method (FIFO + semantic-segment tree + heat-based promotion) — evidence §6 and §8.2 Exp.6, "achieves the best overall performance on both benchmarks... while maintaining a remarkably low computational overhead." Also §8.2 Exp.1(1): tree/hierarchical methods (MemTree, MemOS) top the accuracy tables.
- **Why worth adopting for an NPC memory service:** Baseline explicitly flags "No hierarchical/schema memory (episodic only; no consolidation into semantic summaries beyond reflection-as-endpoint)." Our reconstruction mechanism thins detail by decay band, but there is no intermediate "this cluster of episodes IS a summarized thing now" tier the way MemoryOS's mid-term segment-summary layer works.
- **Adoption cost/risk in our stack:** Large — this would mean a genuinely new storage tier (not just an index), with its own promotion/demotion policy and its own retrieval path. This is squarely adjacent to (but distinct from) the already-designed-but-not-built reflection pipeline; likely the natural home for this idea is as an input into that future spec rather than a standalone addition.
- **Docs it would touch:** `architecture.md` §7/§9 (reflection), a future `docs\reflection.md`.
- **Confidence:** Medium (clear payoff in the paper's own benchmarks; less clear how cleanly it composes with our non-destructive/versioned-fact-chain design without becoming a second, competing summarization mechanism).

- **Capability:** Structure-based (graph/multi-hop) retrieval as a first-class retrieval paradigm alongside vector search.
- **What the paper does:** Mem0 explores relationships from similarity-search seed nodes to build a subgraph; Zep runs BFS graph traversal to expand initial vector results — evidence §7, "Structure-Based Retrieval."
- **Why worth adopting for an NPC memory service:** Same underlying gap as "Connecting" above (no graph exists yet), but this is specifically about the *retrieval-time* payoff once such a structure exists — multi-hop chains ("the memory that explains why this other memory happened") become directly queryable instead of relying on top-k similarity coincidentally surfacing both.
- **Adoption cost/risk in our stack:** Strictly depends on the Connecting capability above being built first; not independently adoptable.
- **Docs it would touch:** Same as Connecting, above.
- **Confidence:** Medium (contingent on a prerequisite that doesn't exist yet).

### THESIS-TENSION flags (conflicts with an invariant — surface, don't force)

- **Invariant challenged:** #8, "The retrieval gate is non-LLM. No gate model, no gate env var."
- **What the paper does that conflicts:** Names "LLM-Assisted Retrieval" as one of four first-class retrieval paradigms — "LLMs can also be utilized to transform ambiguous user prompts into precise search queries or to identify key entities within a query to facilitate more targeted retrieval" (§7).
- **Honest read:** This is a genuine, evidenced capability (the paper's own related discussion of LLM-Assisted Retrieval frames it as excelling at "uncovering latent semantic dependencies") that we deliberately forgo. It is a positioning trade-off already made and explained in our docs (determinism, cost, latency, testability of a non-LLM gate) — not an oversight. Flagging honestly rather than silently dropping, per the reduce-step contract.

### Verdict
Medium-High priority overall: the paper doesn't hand us a single drop-in upgrade, but it (a) empirically validates two of our biggest architectural bets (non-destructive storage, one-live-head fact chain) against real failure modes other systems exhibit, and (b) sharpens two already-known baseline gaps (no graph/connecting structure, no hierarchical tier) with concrete measured payoff and named exemplar systems (MemTree, MemoryOS, Zep, Mem0) to study before any future spec session on either. **P2 worth-piloting:** hybrid lexical+vector retrieval (cheap, additive, doesn't touch scoring invariants). **P3 note-only / future-spec-input:** the graph/connecting capability and the hierarchical-tier capability — both real, both big enough to need their own dedicated spec sessions rather than a bolt-on.
