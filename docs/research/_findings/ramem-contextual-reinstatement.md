# RaMem: Contextual Reinstatement for Long-term Agentic Memory

- **Authors / venue / year:** Wei Yang, Bryce Kan, Shixuan Li, Li Li, Yuehan Qin, Jiate Li, Paul Bogdan, Jesse Thomason (University of Southern California) — 2026, arXiv preprint.
- **arXiv / DOI:** arXiv:2606.22844v1 — https://arxiv.org/abs/2606.22844
- **Source:** discovered
- **Overall relevance to longmem-npc:** High — names and empirically measures exactly the gap our read-path already anticipated but left reserved: our retrieval accepts `location`/`entities`/`event_time` as query-side context "accepted-but-reserved (future encoding-context term)" without consuming them; RaMem is a worked-out, benchmarked design for consuming that same class of signal at the memory (not just query) side, plus a query-side "recall condition" decomposition we don't have at all.
- **Core contribution (2-3 sentences):** RaMem identifies "context collapse" — retrieved memory fragments that are semantically related to a query but belong to the wrong episode (wrong time, session, or participants), so they compete as false-positive evidence even when a relevance-only retriever ranks them highly. It fixes this with a four-stage pipeline: anchor each memory to its episodic context (event time, mention time, session span, participants) at write time; decompose each query into an information need plus a "recall condition frame"; retrieve with those conditions used as a priority filter (not a hard constraint, activated only when conditions are reliably grounded) with content-relevant results kept as fallback; and pass the selected memories to the generator with their structured context still attached rather than flattened to plain text. Across LoCoMo/LongMemEval and four backbones this yields >10 F1 points average gain over the strongest structured-memory baseline (SimpleMem), and a targeted "context shuffle" ablation confirms the gain comes from genuine content-context binding, not just extra metadata volume.

### Mechanisms relevant to us
- **Episodic Memory Anchoring** (§3.1): each memory is stored as `(content, episodic_context)` where the context field explicitly separates `event_time` (when the described event happened) from `mention_time`/`session_span` (when it was *observed/recorded*) — plus participants, location, entities, topic. This event-time-vs-mention-time split is a sharper version of a distinction our schema already gestures at (`event_time` column exists, reserved) but doesn't currently use to disambiguate competing candidates.
- **Recall Condition Induction** (§3.2): decomposes a query into an information need (`r_q`) and a separate "recall frame" (`c_q`) of grounded constraints (time range, participants, location, entities, topic) that a *valid* supporting memory must satisfy — this is the query-side half of the mechanism our baseline has no analogue for at all (our query is `query_text` embedded as-is; location/entities/event_time are accepted fields but never parsed into constraints).
- **Validity-Aware Retrieval with selective activation** (§3.3): session-overlap compatibility check (`s_start ≤ t_end AND s_end ≥ t_start`, with a tunable buffer) used to re-rank/filter candidates, but *only* triggered when recall conditions are reliably grounded — falling back to pure content retrieval otherwise, with content-relevant candidates always retained as fallback evidence rather than hard-excluded. This graceful-degradation shape (soft priority, not hard filter; explicit fallback) is compatible with our existing fail-quiet philosophy.
- **Context-Preserved Synthesis** (§3.4): retrieved memories are passed to the generator *with* their structured episodic coordinates still attached (session span, event time, participants, location), not reduced back to flat prose — their ablation shows this alone matters: "removing context-preserved generation leaves retrieval metrics unchanged by design, but reduces F1 from 0.5957 to 0.5626" (Table 4), i.e. correct retrieval is necessary but not sufficient; the context has to survive into the prompt.

### STRICTLY-BETTER candidates (beats a mechanism we already have)
- **Component touched:** Read path / retrieval scoring (`app\retrieval.py`) — specifically the currently-inert reserved context fields.
- **Our current mechanism:** "Query = `query_text` embedded as-is; location/entities/event_time accepted-but-reserved (future encoding-context term)" (baseline §Read path). No temporal or participant compatibility filtering exists; over-fetch is purely distance-based, re-ranked by relevance × recency × importance.
- **Paper's mechanism:** Session-overlap temporal compatibility check used as a *priority* signal (not hard filter) over distance-retrieved candidates, activated only when the query's temporal cues can be grounded — *evidence:* §3.3, Eq. 4, "memory m_i is temporally compatible if s_start ≤ t_end^q AND s_end ≥ t_start^q"; §4.3 "Context Collapse Analysis" shows a baseline retriever (SimpleMem) ranks a context-incompatible-but-topically-related memory first in 43.66–54.14% of confusable cases, and RaMem cuts that (D@1) roughly in half across backbones.
- **Why strictly better:** This is a concrete, benchmarked answer to exactly the gap our own docs flag as reserved-but-unimplemented. It doesn't require abandoning our relevance × recency × importance formula — it's a compatible additional re-ranking signal (or a soft prior term) that specifically targets the failure mode of two memories about "similar" content from different times/participants competing for the same retrieval slot, which our current design has no defense against once both clear the relevance bar.
- **Adoption cost/risk in our stack:** Low-to-moderate. We already store `event_time`, `location_name`, `entities` per memory (write-time facts, per the fact-level-correction scoping) and the read path already accepts (but ignores) query-side `location`/`entities`/`event_time`. Implementing session-overlap-style compatibility would mean: (1) deciding what "mention time" means for us (likely `memories.created_at`, already present), (2) adding a compatibility term to the read-path scoring function (config-driven weight/buffer, per our "nothing hardcoded" invariant), (3) NOT hard-filtering (matches our fail-quiet philosophy and RaMem's own selective-activation design). No schema migration required — this is a scoring-function change over columns we already have.
- **Docs it would touch:** `docs\read-path.md`, `docs\architecture.md` §6 (the reserved encoding-context term is explicitly named there as a future slot this would fill).
- **Confidence:** Medium-High — the mechanism is simple and directly portable; the main open design question (not answered by the paper, since it's for human-assistant dialogue rather than a game world) is what an NPC-relevant "recall condition frame" should look like — likely simpler than RaMem's LLM-based query decomposition, perhaps just structured fields already available from the game client (current location, current scene entities) rather than parsed from `query_text`.

### NOT-YET-BUILT candidates (a capability we simply don't have)
- **Capability:** Query-side "recall condition" decomposition and participant/location-aware evidence filtering — none / gap noted in baseline as the encoding-context term being merely "reserved" with no consumption logic at all, query or memory side.
- **What the paper does:** Splits every incoming query into an information need plus explicit recall constraints (temporal range, participants, location, entities) derived via LLM analysis of the query, used to construct a priority-ordered, context-compatible candidate list — *evidence:* §3.2, "the recall frame separates the requested information from the evidence conditions that a supporting memory should satisfy," with a worked example ("What did Sarah decide after the appointment in late March?" → participant=Sarah, temporal="late March", relation="after").
- **Why worth adopting for an NPC memory service:** Player dialogue naturally contains this same ambiguity ("what did you think of that place we visited?") where the wrong-episode memory (a different visit, a different companion) can be topically closer than the right one. This capability is a natural full realization of what our reserved fields were designed for from the start.
- **Adoption cost/risk in our stack:** Higher than the strictly-better item above, since it requires either an LLM call to decompose `query_text` into constraints (a new model-role decision, config-gated per our "every model role has its own env var" rule) or a simpler client-supplied-fields approach (game client already knows current location/scene participants, which may make an LLM decomposition unnecessary for us — a genuinely cheaper path than RaMem's, worth flagging as a design fork rather than a straight port).
- **Docs it would touch:** `docs\read-path.md`, `docs\architecture.md` §6.
- **Confidence:** Medium — concept is sound and gains are demonstrated, but the query-decomposition mechanism itself is tuned for open-domain human-assistant conversation; an NPC-service version would likely look different enough (structured client context vs. parsed free text) that this is a "not yet built, and not directly portable" finding rather than a "port this code" finding.

### THESIS-TENSION flags (conflicts with an invariant — surface, don't force)
*(none — RaMem operates entirely on the read/retrieval side and doesn't touch storage mutability, decay, or reconstruction; it's compatible with non-destructive storage since episodic context is additional metadata on immutable records, not a replacement mechanism.)*

### Quotable lines / citations for positioning (optional)
- "a memory can be related to the query while still being invalid evidence for it" (§3.3) — sharp framing line, useful for describing the difference between relevance and validity in our own docs (distinct from, but complementary to, our importance-vs-relevance independent-axes invariant).
- "Episodic memory and encoding specificity emphasize that retrieval is shaped by the match between a cue and the context in which the experience was encoded [Tulving, 2002]" (§1) — directly cites encoding specificity, the same psychological concept our own reserved "encoding-context read term" is named after; useful corroboration that this is a recognized research direction, not a speculative one.

### Verdict
P1/P2: the temporal/participant compatibility re-ranking signal (strictly-better item) is a low-cost, high-fit addition that directly fills a slot our own architecture already reserved and named — worth considering as a scoped read-path enhancement task when that reserved term is next revisited. The fuller query-decomposition capability (not-yet-built item) is P2 worth-piloting, likely in a simplified client-context form rather than RaMem's LLM-decomposition form.
