# MemTrace: Probing What Final Accuracy Misses in Long-Term Memory

- **Authors / venue / year:** Xianxuan Long, Zhikai Chen, Shenglai Zeng, Shouren Wang, Kai Guo, Jiliang Tang (Michigan State University, Case Western Reserve University) — preprint, 2026.
- **arXiv / DOI:** 2606.17328v1
- **Source:** discovered (second-wave sweep, Lane B)
- **Overall relevance to longmem-npc:** High — adds a genuinely new construction methodology to our named eval-harness gap (Table 2 #1 in `FINDINGS.md`): a **fact-fixed, multi-axis probing protocol** plus a **reach-vs-use diagnostic** that none of LongMemEval/LoCoMo/MemoryAgentBench/STALE/MemConflict/Memora/MemSyco supply in this form.
- **Core contribution (2-3 sentences):** Instead of scoring accuracy per question row, MemTrace fixes the unit of measurement at the **knowledge point** (a single typed fact about the user) and probes each one along three controlled, orthogonal axes: memory age (how many sessions since it first appeared), question type (current state / earlier state / trajectory-of-change), and evidence condition (present / missing / contradicted by a false premise). Across 13 memory systems, it finds that pooled accuracy hides genuinely different failure modes — recovering a fact's current and earlier states does not imply the system can narrate how it changed, and "safe abstention" on missing facts does not imply the system can correct a false premise — and that the dominant bottleneck, when systems fail, is **evidence use, not retrieval** (gold evidence was retrievable ~10x more often than it was missing).

### Mechanisms relevant to us

- Knowledge-point (fixed-fact) unit of measurement, expanded into controlled probes rather than independent question rows (§3, Table 1 comparison against LoCoMo/LongMemEval/PersonaMem/HaluMem/MemoryAgentBench — MemTrace is the only row with "Same fact across age windows" ✓ + "Same fact across question types" ✓ + "Failure attribution: reach vs. use" ✓ simultaneously).
- Three-axis probe construction (§3.2): memory age via 8 chronological checkpoint windows (not disjoint blocks — a continuous retention trace, with extra windows anchored near dynamic updates to catch pre/post-update state); question type (current/historical/**trajectory**); evidence condition (present/missing/conflict, the last two built from held-out "distractor" knowledge points).
- Score tuple, not a single accuracy number (§3.3): `(g, v, r)` — binary **Gist accuracy** (semantic correctness), continuous **Verbatim completeness** in [0,1] (canonical-token presence), and categorical **Response type** (correct / abstention / hallucination), judged primarily by GPT-4o with a second-model (Gemini-3-Flash) reliability check on a stratified 200-probe sample under the same rubric.
- Three named diagnostic *views*, reported separately rather than blended (§3.4): (1) **memory maintenance** — Fresh (checkpoints 1-2) vs Saturated (checkpoints 7-8) accuracy, with "Forget" as their gap, computed per question type; (2) **evidence-condition behavior** — boundary-abstention rate and conflict-Gist rate reported as two independent axes, not one abstention score (§4.3, Figure 4: systems can be "boundary-safe" at 94-99% abstention while resolving false-premise conflicts only 15-35% of the time — "abstaining is not resolving"); (3) **failure attribution** via a reach-vs-use replay: a cheap standalone retriever checks whether gold evidence was reachable at all, then an "oracle" open-book pass re-scores hard failures with the evidence supplied directly, separating retrieval-reach misses from reached-but-unused evidence.

### NOT-YET-BUILT candidates (a capability we simply don't have)

- **Capability:** A judged eval harness (our own baseline names this as the biggest gap). MemTrace contributes construction/rubric techniques not present in the papers we already hold.
- **What the paper does:** Fixes the fact, varies the conditions, scores a 3-tuple, and diagnoses failures by replaying with a cheap retriever + an evidence-supplied oracle — *evidence:* §3 "MemTrace uses knowledge points as the analysis unit. Each fact is probed across windows, question types, and evidence conditions, so behavior is measured on the knowledge point rather than averaged across independent question rows"; §3.4 "When a system answers incorrectly, we ask whether the gold evidence was unreachable or reachable but unused... across systems, the main bottleneck is evidence use rather than retrieval: failures come 10x more often from unused evidence than from unreachable evidence."
- **Why worth adopting for an NPC memory service:** Three pieces genuinely extend rather than duplicate our existing shortlist (LongMemEval's knowledge-update category, LoCoMo's FactScore-retargeted reconstruction eval, MemoryAgentBench's FactConsolidation): (1) the **trajectory** question type ("how did this change over time") is a probe our architecture is unusually well-suited to answer, since we already maintain an explicit, queryable version chain (`memory_details` write_cause chain + `memory_fact_versions`) purpose-built to narrate drift — none of our existing eval papers test narrating-the-change as its own category, only final-state correctness; (2) the **reach-vs-use diagnostic** maps directly onto our own pipeline seam — it would let us tell whether a failure is a gate/retrieval problem (`app/gate.py`, `app/retrieval.py`) or a dialogue-call prompt-assembly/generation problem (`app/dialogue.py`), which our structural pytest suite cannot distinguish since it never judges model output quality; (3) the **two-axis evidence-condition reporting** (boundary-abstention rate vs conflict-resolution rate as separate numbers) sharpens our existing Table 2 #1 abstention recommendation — it gives empirical grounds (94-99% boundary-safe vs 15-35% conflict-resolved, same systems) for why a single blended "abstention score" would hide the exact failure mode ("controlled infidelity" drifting into either silent non-answers or false-premise-following) we most need to catch. Memory-age checkpointing (repeated probes at 8 points across a growing history, with extra windows anchored near updates) is also a directly reusable construction pattern for exercising our decay/reconstruction-band and `as_of` machinery at multiple points rather than one.
- **Adoption cost/risk in our stack:** Low-to-moderate — this is harness/rubric design, not schema or model-role work (no new migration, no new invariant risk). The main cost is authoring: constructing knowledge points with session anchors + distractor pairs against our own fixture NPC data, and a judge-model role (its own env var, per invariant #5) for the (g, v, r) scoring — the same cost class already scoped for the P1 eval-harness recommendation, not additive complexity on top of it.
- **Docs it would touch:** New `docs\eval-harness.md` (construction section), alongside the existing LongMemEval/LoCoMo/MemoryAgentBench citations already slated there.
- **Confidence:** High.
