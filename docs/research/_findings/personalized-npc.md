## Personalized Non-Player Characters: A Framework for Character-Consistent Dialogue Generation

- **Authors / venue / year:** Xiao Liu, Zhenping Xie, Senlin Jiang (Jiangnan University / Wuxi Institute of Technology); *AI* (MDPI) 2025, 6, 93
- **arXiv / DOI:** https://doi.org/10.3390/ai6050093
- **Source:** folder
- **Overall relevance to longmem-npc:** High — this is the closest of the four papers to our actual problem shape: character-consistent dialogue generation backed by an explicit two-tier memory system with retrieval, consolidation, and forgetting. Distinct architecture (fine-tuned model + knowledge graph, not our prompted-API + Postgres/pgvector), so most findings are "not-yet-built capability" rather than "drop-in improvement."
- **Core contribution (2-3 sentences):** Combines (1) "protective" LoRA fine-tuning so an NPC model expresses ignorance/confusion about out-of-character topics instead of hallucinating, and (2) a dynamic short-term Knowledge Graph (Neo4j, entities+relations, access-frequency-based consolidation/forgetting) + long-term vector DB (Qdrant), fused with an AMR (Abstract Meaning Representation) semantic parse of the player's input to retrieve and rank relevant memory before generation. Reports gains over profile-card and KG-augmented baselines on hallucination/memory/personality metrics via LLM-judge.

### Mechanisms relevant to us
- **Two-tier memory with access-frequency-driven consolidation/forgetting** (§3.4, Algorithm 2, Table 4): short-term KG nodes decay (deleted) if accessed <3 times in 24h; nodes accessed ≥5 times in 7 days are promoted/copied into the long-term vector store; the rest are pruned. Modeled explicitly on Ebbinghaus + the "five-times memory rule."
- **Dynamic knowledge graph as the memory substrate** (§3.2.1): entities/attributes/relationships as nodes/edges in Neo4j, built by prompting an LLM to structure weekly experience summaries into graph form.
- **AMR-based query understanding** (§3.2.1-3.2.3): player input parsed into an AMR semantic graph (SpringAMR/BART), core `ARG0`/`ARG1` (agent/patient) nodes matched against the character KG via node-embedding cosine similarity, fused and *pruned* to just the ARG0/ARG1-connected subgraph before being encoded and used to retrieve from the vector store.
- **Protective fine-tuning against character hallucination** (§3.1.2, Table 2): adversarial training scenarios where the model is provoked with out-of-character questions and trained to respond with in-character confusion/refusal rather than fabricated knowledge; ablation shows ~34% additional hallucination-metric improvement over knowledge-fine-tuning alone.
- **Evaluation**: LLM-judge (gpt-4o) scoring three axes — Hallucination, Memorization (mCor.), Personality (Per.) — 7-point Likert, reported per-character and per-base-model (§4, Tables 6/8/9).

### STRICTLY-BETTER candidates (beats a mechanism we already have)
*(none)* — no mechanism here beats a *named* component of our built pipeline on its own terms; the KG-based memory is architecturally simpler than our bi-temporal fact/detail chain (flat nodes, no versioning, no importance/decay math), and the consolidation mechanism is destructive (see THESIS-TENSION below), which our design already deliberately avoids.

### NOT-YET-BUILT candidates (a capability we simply don't have)
- **Capability:** An associative/graph structure over memory content — baseline names this gap explicitly: "No graph / associative structure over memories (no entity graph, no linking beyond identity-components + gist spans + entities[]). No multi-hop retrieval."
- **What the paper does:** A dynamic entity-relationship knowledge graph (Neo4j) is the actual memory substrate; retrieval fuses the player-input's parsed semantic graph with matched KG subgraphs via a graph-matching + pruning algorithm (Algorithm 1, §3.2.2) rather than flat top-k vector similarity alone — e.g., "the system retrieves semantically similar nodes from the constructed character knowledge graph... Erel = {e ∈ Ekg | head(e) ∈ S ∧ tail(e) ∈ S}" (Algorithm 1).
- **Why worth adopting for an NPC memory service:** Our `identity_components` + `entities[]` text arrays give lookup and tripwire matching but no edges/relationships between entities (no "X owns Y," "X is angry at Y" as a queryable structure) and no multi-hop traversal. A relationship graph would let retrieval/gate reasoning follow a chain (e.g., "the player mentioned the blacksmith's daughter" → traverse to the blacksmith → traverse to the guild feud) that pure embedding similarity or single-entity GIN lookups can't express.
- **Adoption cost/risk in our stack:** Substantial — a new table/edge model (migration), a graph query layer (Postgres has no native graph engine; would need recursive CTEs or an extension), and it would need to be designed non-destructively from day one (see tension below) rather than ported as-is. This is a real schema-evolution candidate, not a small addition.
- **Docs it would touch:** `architecture.md` (new §, memory-graph design), a new migration spec, `mid-dialogue-gate.md` (the entity tripwire is the natural first consumer of edges, not just node hits).
- **Confidence:** Medium — the capability gap is real and named in our own baseline, but this paper's specific implementation (destructive consolidation, no bi-temporal treatment) isn't a template we'd port; it's evidence the *capability* is worth designing, not a ready mechanism.

- **Capability:** Structured semantic parsing of player/query input (entities + predicate-argument roles) as an alternative/complement to raw-text embedding for retrieval and gate-trigger extraction.
- **What the paper does:** AMR parse of input → ARG0/ARG1 role extraction → matched against KG nodes → pruned to the core-argument subgraph before encoding (§3.2.2-3.2.3, Algorithm 1). Ablation (Table 6) shows the pruned AMR⊕KG graph gives the best accuracy/hallucination-suppression tradeoff versus KG-only or unpruned-fusion variants.
- **Why worth adopting for an NPC memory service:** Our read-path's `query_text` is "embedded as-is," and the gate's entity tripwire relies on NLP span/entity matching (spaCy), not role-labeled semantic parsing. An AMR- or dependency-role-based extraction of the player's utterance (who did what to whom) could sharpen the gate's entity-tripwire precision and the reserved encoding-context read term, distinguishing e.g. "the guard hit the merchant" from "the merchant hit the guard" — a distinction our current entity-list matching can't make.
- **Adoption cost/risk in our stack:** Medium — would need a new NLP component (AMR parser is a real dependency, license/perf unverified against our Apache-2.0 flip gate) or a lighter dependency-parse substitute using the existing spaCy pipeline. No schema change required; this is a write/read-time NLP-pass enhancement.
- **Docs it would touch:** `mid-dialogue-gate.md` (entity tripwire), `read-path.md` (query encoding, currently reserved slot).
- **Confidence:** Low-Medium — plausible precision gain, unverified for our specific entity-tripwire use case, and adds a real NLP dependency we'd need to license-gate check.

### THESIS-TENSION flags (conflicts with an invariant — surface, don't force)
- **Invariant challenged:** Non-destructive bi-temporal storage ("Never DELETE... purge endpoint is the sole exception").
- **What the paper does that conflicts:** The two-tier forgetting mechanism literally deletes graph nodes/edges: "it clears nodes in the knowledge graph that have not been accessed and have a total call count of less than 3 in a certain time period... eliminating other low-frequency nodes that have not been accessed for a long time" (§3.4); Algorithm 2 step 5 is explicit set-removal: `V ← V \ {v}` — *evidence:* §3.4, Algorithm 2, lines 15-24.
- **Honest read:** This is a genuine architectural difference, not an apples-to-oranges mismatch — both systems solve "what does the character remember and how does old/low-value information stop cluttering retrieval." Their answer is destructive pruning keyed on access-frequency; ours is recency-decay (read-time, reversible, original always on disk) plus a separate immutable gist layer that never decays. Their approach is simpler to implement and bounds storage growth harder, at the cost of unrecoverable memory loss and no debug/audit trail — a real weakness by our own invariant's logic, but a reasonable engineering tradeoff for a system that isn't trying to support ground-truth reconstruction or corrections. If we ever adopt graph-structured memory (see NOT-YET-BUILT above), the consolidation/pruning logic would need to be redesigned as bi-temporal invalidation of edges, not deletion — a real design cost to price honestly, not a blocker to the underlying graph idea.
