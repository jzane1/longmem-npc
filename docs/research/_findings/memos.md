# MemOS: A Memory OS for AI System

- **Authors / venue / year:** Li, Xi, Li, Chen, et al. (MemTensor / multiple institutions) — arXiv 2025 (v4, Dec 2025)
- **arXiv / DOI:** arXiv:2507.03724v4
- **Source:** folder
- **Overall relevance to longmem-npc:** Low-Medium — MemOS is a broad systems paper aimed at unifying three heterogeneous LLM memory *substrates* (parameter weights, KV-cache/activation state, and plaintext) under one OS-style scheduler, for general-purpose, multi-user, multi-model AGI infrastructure. Most of its machinery (LoRA/parameter editing, KV-cache paging, cross-user ACLs) targets problems our single-agent, single-model, no-fine-tuning NPC service doesn't have. The one piece that transfers is the evaluation-benchmark suite it validates against, which speaks to a gap our baseline names outright.
- **Core contribution (2-3 sentences):** MemOS proposes treating memory as a first-class, schedulable OS resource across three types — plaintext, activation (KV-cache), and parameter memory — via a "MemCube" abstraction (payload + lifecycle/provenance/access metadata) and a three-layer architecture (Interface/Operation/Infrastructure) with modules like MemScheduler, MemLifecycle, and MemGovernance. It reports state-of-the-art results on LoCoMo, LongMemEval, PreFEval, and PersonaMem against strong memory-system baselines (Mem0, Zep, MIRIX, Memobase, Supermemory, MemU).

### Mechanisms relevant to us
- **Standardized long-term-memory benchmark suite:** LoCoMo, LongMemEval, PreFEval, PersonaMem, each with defined metrics (LLM-judge score, F1, personalized-response rate, precision) used to compare memory systems head-to-head (§6, Tables 3-6, p.24-25).
- **MemLifecycle state machine:** each memory unit transitions Generated → Activated → Merged → Archived/Expired based on access patterns, with a "Frozen" state for critical/legal-grade memories where "updates are disabled and full modification histories are retained for auditing" and a "Time Machine" snapshot/rollback capability (§5.4.3, p.21-22).
- **Hybrid retrieval:** MemOperator combines rule-based tag/time/Boolean filtering with embedding-based semantic search, composable into one query (§5.4.1, p.20).
- **Cross-substrate transformation (parameter ↔ activation ↔ plaintext):** e.g. distilling frequently-used plaintext into LoRA adapters, or promoting hot plaintext into KV-cache (§4.1, §5.4.2, p.13-14, 20-21) — this is the paper's main technical contribution but depends on model fine-tuning/adapter infrastructure.

### STRICTLY-BETTER candidates
*(none identified with enough algorithmic specificity to adopt — the paper describes these mechanisms at a systems/architecture level with benchmark results, but does not publish the concrete decay formulas, conflict-resolution logic, or scoring functions needed to compare them against our specific `app\decay.py` / `app\retrieval.py` math. Its "forgetting policies," "conflict detection," and "temporal decay" are named as capabilities of the Plaintext Memory layer (§4.1, p.13) but never specified in a way that beats our stated `tau_effective = tau_base × (1 + k·importance_raw)` decay or our relevance×recency×importance scoring.)*

### NOT-YET-BUILT candidates

- **Capability:** An end-to-end accuracy/recall evaluation harness benchmarked against established long-term-memory tasks.
- **What the paper does:** Evaluates against LoCoMo (single/multi-hop, temporal reasoning, open-domain LLM-judge scores + F1), LongMemEval (six scenario categories incl. knowledge updates and temporal reasoning), PreFEval (personalization under injected irrelevant turns), and PersonaMem (dynamic-profile precision) — all with published metric definitions and baseline comparisons (§6.1-6.2, Tables 3-6).
- **Why worth adopting for an NPC memory service:** Our baseline states outright: *"No end-to-end evaluation harness. Only a structural pytest suite exists — no LongMemEval-style accuracy/recall benchmark, no judged-drift / Bartlett-style eval, no memory-conflict or staleness eval."* MemOS's use of LongMemEval in particular (a benchmark already named in our own research track) demonstrates a concrete, replicable methodology for measuring knowledge-update handling and temporal reasoning — exactly the categories our reconstruction/correction mechanisms claim to improve but currently have no accuracy evidence for, only structural (assertion-level) tests.
- **Adoption cost/risk in our stack:** Low-to-medium. These are academic QA-style benchmarks (Wikipedia/dialogue corpora), not NPC-dialogue-shaped, so they'd need adaptation or a parallel NPC-specific eval design — but the metric methodology (recall@k, LLM-judge scoring, F1) and the discipline of holding out a knowledge-update category are directly reusable. No schema or invariant changes needed; this is purely an evaluation-harness addition, orthogonal to the storage/retrieval code.
- **Docs it would touch:** would live in the still-unbuilt evaluation harness (named in "Known gaps" but with no owning doc yet) — likely a new `docs\eval-harness.md`.
- **Confidence:** Medium — the benchmarks are real and well-specified, but MemOS's own numbers are self-reported against baselines it also reproduced, so treat the comparative rankings skeptically; the *methodology* (what to measure, how to define recall/knowledge-update categories) is the actual transferable asset, not the specific scores.

### THESIS-TENSION flags

- **Invariant challenged:** none of our numbered invariants directly — but the paper's central mechanism (cross-substrate memory: parameter memory via LoRA/adapters, activation memory via KV-cache injection) is out of scope for our fixed stack in a way close to the "no ORM/no query builder"-style fixed-constraint list, even though it isn't named as an invariant per se.
- **What the paper does that conflicts:** MemOS routes "stable, frequently accessed" plaintext memory into model *parameter* patches (LoRA) or *KV-cache* activation state for performance (§4.1, §5.4.2) — this requires per-agent model fine-tuning/adapter infrastructure and direct KV-cache manipulation, neither of which exists in (or is planned for) our stack of per-role API-called models (importance/render/typology/escalation/dialogue/reconstruction, each "its own env var"). The baseline explicitly notes a second local embedding model would already collide with the locked 1536 dimension; parameter-level model editing per NPC is a much larger commitment in the same direction.
- **Honest read:** This is an apples-to-oranges positioning gap rather than a design weakness — MemOS is solving a different problem (general-purpose, multi-user AGI infra with model-editing budget) than a self-hostable, integrator-run NPC memory service built entirely on prompted API calls. Nothing here should be read as "we're missing something MemOS has"; it's a different point in the design space that happens to share the word "memory OS."

### Quotable lines / citations for positioning
- §1, p.4: *"the key to enhancing memory in LLMs is not simply 'adding a cache' or 'attaching an external retrieval module,' but redefining the operational logic and resource management of memory from a systems-level perspective"* — useful framing quote for a related-work section distinguishing "memory as OS resource" framings from our "memory as psychology" framing.
- §5.4.3, p.22: the "Frozen" state description (*"updates are disabled and full modification histories are retained for auditing, compliance, or education"*) is a nice independent validation of the *value* of an immutable, fully-retained history — congruent with, though arrived at from a compliance angle rather than a confabulation-research angle, our own non-destructive invariant.

### Verdict
P3 note-only: the one actionable item is adopting LongMemEval/LoCoMo-style evaluation methodology to fill the named eval-harness gap (worth a look when that harness gets built), but the paper's core memory-OS/cross-substrate architecture targets a different deployment shape (multi-user, fine-tuning-budget AGI infra) than longmem-npc and shouldn't be mined further for mechanism ideas.
