# Memory in the Age of AI Agents: A Survey — Forms, Functions and Dynamics

- **Authors / venue / year:** Hu, Liu, Yue, Zhang, et al. (NUS, Renmin, Fudan, Peking, NTU, Tongji, UCSD, HKUST-GZ, Griffith, Georgia Tech, OPPO, Oxford) — 2026.
- **arXiv / DOI:** arXiv:2512.13564v2 [cs.CL]
- **Source:** folder (`Memory in the Age of AI Agents.pdf`)
- **Overall relevance to longmem-npc:** High — this is the most comprehensive taxonomy available of *why* and *how* agent memory operates (Forms / Functions / Dynamics), and its Functions taxonomy in particular exposes an entire capability class (experiential/procedural memory) that longmem-npc has zero coverage of, plus a Dynamics (Evolution) taxonomy that names automatic-conflict-resolution and frequency-based-forgetting mechanisms more advanced than our current correction/decay pipeline.
- **Core contribution (2-3 sentences):** Proposes a "Forms (token-level / parametric / latent) × Functions (factual / experiential / working) × Dynamics (formation / evolution / retrieval)" unified taxonomy explicitly replacing the coarse long-term/short-term split used by prior surveys, catalogues representative systems and benchmarks under each cell, and closes with eight forward-looking research frontiers (generative memory, automated management, RL-driven memory, multimodal, multi-agent shared memory, world models, trustworthy memory, human-cognitive parallels).

### Mechanisms relevant to us
- **Functions taxonomy** (§4, Fig. 6): Factual Memory (user-factual / environment-factual) vs. **Experiential Memory** (case-based / strategy-based / skill-based / hybrid) vs. Working Memory (single-turn / multi-turn). Longmem-npc is *entirely* Factual Memory, specifically the "Dialogue Coherence" user-factual sub-type (§4.1.1) plus a sliver of environment-factual (the `identity_components` world-entity index). We have zero Experiential Memory — no mechanism accumulates "what worked" across dialogue turns/scenes.
- **Memory Evolution taxonomy** (§5.2, Fig. 9): Consolidation (local / cluster / global fusion) / Updating (external-memory conflict resolution / model editing) / Forgetting (time-based / frequency-based / importance-driven). We do Updating (correction verbs) and Forgetting (time+importance decay only), but **no Consolidation at all** — nothing merges related raw memories into a new higher-level summary record; reflection (designed, not built) only revises identity prose, it does not consolidate memory *records*.
- **Memory Retrieval taxonomy** (§5.3, Fig. 10): Timing & Intent / Query Construction (decomposition, rewriting) / Retrieval Strategies (lexical/semantic/graph/generative/hybrid) / Post-Retrieval Processing (re-ranking, aggregation). Our gate (`app\gate.py`) covers "Timing & Intent" non-LLM; we do zero Query Construction (query embedded verbatim, by 2026-07-14 ruling); Retrieval Strategies is vector-only (same finding as the companion `survey-llm-era.md`).
- **Updating, specifically** (§5.2.2): "Early systems such as MemGPT, D-SMART, and Mem0g followed a straightforward pipeline in which the LLM detects conflicts between new information and then invokes replace or delete operations... Zep introduced temporal annotations, marking conflicting facts with invalid timestamps rather than deleting them, thereby preserving both semantic consistency and temporal integrity. This marked a shift from hard replacement to soft, time-aware updating." Zep's mechanism is structurally identical to our bi-temporal `invalid_at` supersede pattern — except Zep's is **triggered automatically when new information contradicts a stored fact**, whereas our supersede only fires from an explicit operator/diegetic verb naming a target `memory_id`. There is no path today for "the NPC just observed something that contradicts what it already believes" to self-resolve.
- **Forgetting, specifically** (§5.2.3): "Frequency-driven forgetting prioritizes memory based on retrieval behavior, retaining frequently accessed entries while discarding inactive ones... time-based decay captures natural temporal aging, while frequency-based forgetting reflects usage dynamics." Our `tau_effective = tau_base × (1 + k·importance_raw)` has no access-count/retrieval-frequency term at all.
- **Human-Cognitive Connections** (§7.8) is the paper's closing frontier section and is unusually well-aligned with our own thesis framing — see Quotable lines below.
- **Memory Retrieval vs. Memory Generation** (§7.1) frames "generative memory" (retrieve-then-generate: ComoRAG, G-Memory, CoMEM) as an emerging 2026 frontier distinct from classical retrieval. Our reconstruction mechanism is a working instance of exactly this pattern, with an added drift-budget refusal + persisted versioned write-back that the cited systems don't appear to have (they generate ephemeral compressed context per query rather than writing a new, cache-keyed, non-destructively-versioned memory row). Useful for positioning, not an adoption candidate (we already have it).
- **Benchmarks** (§6.1, Table 8): concretely deepens the baseline's "no eval harness" gap with named, adoptable benchmarks — LongMemEval's Knowledge-Updates subtask (memory-conflict recall), HaluMem ("Evaluating Hallucinations in Memory Systems of agents" — also present as its own paper in our `Research Papers\` folder), PersonaMem, PrefEval, DialSim, MemBench. STALE ("Can LLM Agents Know When Their Memories Are No Longer Valid") is directly relevant to our staleness/conflict gap and is also already sitting in our own `Research Papers\` folder as a separate paper.

### STRICTLY-BETTER candidates (beats a mechanism we already have)

- **Component touched:** Correction verbs / dissonance path (`app\ingest.py`, `app\db.py` `apply_authorial_correction`; `docs\authorial-correction.md`, `docs\fact-level-correction.md`).
- **Our current mechanism:** Supersession (stamping `invalid_at`) only happens through an explicit, exogenously-triggered verb: the operator's authorial-correction endpoint, or (designed, not built) a diegetic event that *names a target `memory_id`*. There is no mechanism by which a newly observed fact that contradicts an existing live fact head gets reconciled on its own.
- **Paper's mechanism:** Ingest-time automatic conflict detection with soft, temporal invalidation — evidence §5.2.2 (quoted above in full): Zep "mark[s] conflicting facts with invalid timestamps rather than deleting them," triggered by the system noticing a contradiction, not by an operator naming a row.
- **Why strictly better:** Right now, if the world simply changes and the NPC observes a new, contradicting fact with no explicit correction/diegetic event routing it to the old memory_id, the old and new facts sit side-by-side, distinguished only by decay/recency — not by an explicit "this superseded that" relationship. This risks the NPC's reconstructed telling drawing on both a stale and a fresh contradictory fact within the same decay window, with no signal that they conflict at all (a class of bug LongMemEval's Knowledge-Updates task and the MemConflict paper are built to catch — see Benchmarks above).
- **Adoption cost/risk in our stack:** Requires an ingest-time comparison step — likely entity-keyed (reuse the migration-003 entities column + partial GIN already built for the gate) plus an embedding-distance check against existing live fact heads for the same entities, with a policy for what similarity/entity-overlap threshold counts as "contradiction" (a new integrator-configurable knob, per invariant #5). Fully compatible with the non-destructive invariant (still supersede via `invalid_at`, never delete) and reuses existing infrastructure (entities GIN, fact-head embedding) rather than requiring new storage — but it is a genuine design fork (what counts as a conflict? does it require an escalation-style LLM judgment call, or a pure-vector/entity heuristic like the gate?) that needs its own ruling, not a silent addition.
- **Docs it would touch:** `docs\fact-level-correction.md`, `docs\mid-dialogue-gate.md` (shares entity/GIN infrastructure), `architecture.md` §4.4/§7.
- **Confidence:** Medium-High (mechanism and evidence are concrete; the exact trigger policy is undesigned and is exactly the kind of fork this project's process would want ruled explicitly, not inferred).

- **Component touched:** Decay (`app\decay.py`).
- **Our current mechanism:** `tau_effective = tau_base × (1 + k·importance_raw)`; decay is a pure function of age and write-time importance — never touched by how often (or recently) a memory has actually been retrieved or reconstructed.
- **Paper's mechanism:** Frequency-based forgetting as an orthogonal axis to time-based decay — evidence §5.2.3, "By distinguishing between creation time and retrieval frequency, these two axes form a more orthogonal taxonomy: time-based decay captures natural temporal aging, while frequency-based forgetting reflects usage dynamics, together maintaining system efficiency and recency." (MemOS: LRU; XMem: LFU; KARMA: counting Bloom filters.)
- **Why strictly better:** Cognitively motivated and on-thesis: a memory that keeps getting recalled/reconstructed is, in human terms, a well-worn story that should resist decay more than one that's never touched again — this *strengthens* the reconstruction narrative (frequently-retold memories drift and stabilize differently than rarely-touched ones) rather than being a generic bolt-on optimization.
- **Adoption cost/risk in our stack:** Needs an access/reconstruction-count signal per memory (could piggyback on `reconstruction_cache` hit counting, or a new column), folded into `tau_effective` behind a new configurable knob (e.g. `decay_k_access`), never hardcoded per invariant #5. Additive to the existing formula, doesn't touch the read-time-only / original-stays-on-disk decay contract.
- **Docs it would touch:** `docs\read-path.md` (decay knobs), `architecture.md` §6.
- **Confidence:** Medium (well-evidenced as a general technique across multiple cited systems; not benchmarked against pure time-decay in either survey specifically for a reconstruction-style system like ours).

### NOT-YET-BUILT candidates (a capability we simply don't have)

- **Capability:** Experiential memory — case-based, strategy-based, or skill-based memory that lets an NPC accumulate *how to act* across dialogue turns, distinct from the *what happened* factual record we already store.
- **What the paper does:** §4.2 distinguishes Case-based (raw trajectory/solution replay — Memento, JARVIS-1), Strategy-based (distilled insights/workflows — ReasoningBank, AWM, H2R), and Skill-based (compiled executable procedures — SkillWeaver, Memp) memory, each answering "how does the agent improve?" as opposed to factual memory's "what does the agent know?"
- **Why worth adopting for an NPC memory service:** Baseline's post-August "parameter compiler" (reflection → typed clamped retrieval-weight/action-bias/stance-prior bundle) is the closest analog we have designed, but it's stance/bias tuning, not accumulated strategy ("when the player lies and gets caught, doubling down on suspicion works better than forgiving" is a strategy-memory fact, not an identity fact). This is a distinct capability class from anything in our current design, worth a forward pointer into the reflection/parameter-compiler spec when that work resumes.
- **Adoption cost/risk in our stack:** Large — a new memory kind, its own storage/write path, and its own consumption point in the dialogue call. Not a bolt-on; best treated as an input to the not-yet-specced reflection/parameter-compiler work rather than a standalone build.
- **Docs it would touch:** A future `docs\reflection.md`, `architecture.md` §9.
- **Confidence:** Medium (clear capability gap; unclear how much of it we actually want given the project's game-NPC scope vs. this paper's task-solving-agent framing — flagging, not recommending priority).

- **Capability:** Memory Consolidation — merging related raw memories into a new, higher-level synthesized record (distinct from reconstruction, which re-tells a *single* memory's chain, and distinct from reflection, which revises identity prose).
- **What the paper does:** §5.2.1 — local consolidation (RMM merges near-duplicate topic memories via LLM judgment), cluster fusion (PREMem aligns and fuses semantically related clusters into "higher-order reasoning units"), global integration (MOOM builds a stable role profile from many role snapshots).
- **Why worth adopting for an NPC memory service:** Baseline explicitly notes "No hierarchical/schema memory (episodic only; no consolidation into semantic summaries beyond reflection-as-endpoint)." Without this, ten small related observations stay ten small rows forever (thinned by decay, never synthesized), even though a human would eventually compress them into "she's generally suspicious of me" as its own recallable fact.
- **Adoption cost/risk in our stack:** Must be additive, not destructive, to respect invariant #1 — a consolidated summary would have to be a *new* row alongside (never replacing) its sources, which our append-only schema style already supports in principle. Real scope: needs its own write path, its own trigger (age? cluster size? reflection-driven?), and a policy for how a consolidated memory interacts with gist/decay/reconstruction. Adjacent to, but distinct from, the not-yet-built reflection pipeline.
- **Docs it would touch:** A future `docs\reflection.md` or a new consolidation spec, `architecture.md` §7.
- **Confidence:** Medium (clear gap, clear exemplars; genuinely open how it should compose with the existing gist/fact-chain/reconstruction stack without becoming a second, competing summarization mechanism).

- **Capability:** A named evaluation harness for memory correctness (accuracy/recall, conflict handling, staleness detection, hallucination-in-memory) — deepens (doesn't duplicate) the baseline's own noted gap.
- **What the paper does:** §6.1, Table 8 catalogues LongMemEval (Knowledge-Updates subtask = conflict-recall), HaluMem ("Evaluating Hallucinations in Memory Systems of Agents" — also independently in our `Research Papers\` folder), PersonaMem, PrefEval, DialSim, MemBench, each with a stated methodology for probing exactly the failure modes our baseline lists as untested (memory-conflict, staleness, judged drift).
- **Why worth adopting for an NPC memory service:** Baseline says plainly: "No end-to-end evaluation harness. Only a structural pytest suite exists — no LongMemEval-style accuracy/recall benchmark, no judged-drift / Bartlett-style eval, no memory-conflict or staleness eval." This section names concrete, adoptable methodologies rather than leaving that gap abstract. STALE ("Can LLM Agents Know When Their Memories Are No Longer Valid") is also sitting in our own paper folder and is a direct hit for the staleness-eval gap.
- **Adoption cost/risk in our stack:** Pure addition — a new eval harness distinct from the structural pytest suite (`tests\`), doesn't touch product code. Research-track item, already acknowledged as sequenced-later.
- **Docs it would touch:** None directly yet — feeds the "Research track" line in `docs\status.md`'s sequenced-later ledger.
- **Confidence:** High (this is a documentation/roadmap finding, not a design claim — low risk, high traceability).

### THESIS-TENSION flags (conflicts with an invariant — surface, don't force)

- **Invariant challenged:** #8, "The retrieval gate is non-LLM. No gate model, no gate env var."
- **What the paper does that conflicts:** §5.3.1 "Automated Retrieval Timing" describes fast-slow-thinking retrieval-timing control — ComoRAG and PRIME "first produce a fast response and then let the agent evaluate its adequacy. If the initial reasoning is deemed insufficient, the system triggers deeper retrieval," and MemGen "introduces memory triggers that detect critical retrieval moments from latent rollout states" — i.e., an LLM (or a trained latent policy) decides *whether/when* to retrieve, which is precisely the job our gate does non-LLM via novelty+tripwire+damper.
- **Honest read:** Genuine capability trade-off, not an oversight — these fast-slow and latent-trigger approaches are plausibly more precise (they can catch "I don't actually know this" in a way a fixed cosine threshold can't), but they cost an extra model call (or training investment) per turn and break the gate's current determinism/testability (51-assertion structural walker `tests\verify_gate.py` depends on the gate being a pure function). This is the same trade-off already made and documented for our gate design — surfacing it again here because this survey's evidence for the alternative is stronger/more current than what was likely considered at gate-spec time (2026-07-19), not because it's a new discovery.

### Quotable lines / citations for positioning (optional)
- "Human memory operates as a constructive process, where the brain actively reconstructs past events based on current cognitive states rather than replaying exact recordings (Schacter and Addis, 2007). In contrast, the majority of existing agent memory systems rely on verbatim retrieval mechanisms like RAG, treating memory as a repository of immutable tokens to be queried via semantic similarity... while agents possess a veridical record of the past, they lack the biological capacity for memory distortion, abstraction, and the dynamic remodeling of history that characterizes human intelligence." (§7.8.1, p.76) — this is close to a direct description of the gap our reconstruction mechanism (identity-conditioned reconstructive memory over an immutable record) is built to close; strong candidate for the README/thesis writeup.
- "Ultimately, this evolution suggests a paradigm shift in memory forms and functions: moving from explicit text retrieval to generative reconstruction." (§7.8.2, p.76) — names "generative reconstruction" as the frontier; our project's one-line thesis already claims this territory.
- "Zep... introduced temporal annotations, marking conflicting facts with invalid timestamps rather than deleting them, thereby preserving both semantic consistency and temporal integrity. This marked a shift from hard replacement to soft, time-aware updating." (§5.2.2, p.57) — good comparison point: validates our bi-temporal supersede pattern as the more mature end of the field's own evolution, while also being the direct evidence for the "automatic conflict detection" not-yet-built finding above.

### Verdict
High priority as a map, medium priority as a source of immediately-actionable builds. The single most consequential finding is the **experiential-memory gap** (§4.2) — it names a whole function class (case/strategy/skill memory) genuinely absent from a system that otherwise covers factual memory unusually thoroughly, and it should inform the reflection/parameter-compiler spec whenever that work resumes (P2, but sequenced — don't pull forward without a concrete trigger). The **automatic conflict detection** and **frequency-informed decay** findings are the two with a clear, scoped, invariant-compatible path to a future migration (P2 worth-piloting, each deserving its own explicit-question ruling before build, per this project's fork-presentation discipline). The benchmark catalogue (§6.1) is low-risk, high-value reading list material for the sequenced-later eval-harness item (P3 note-only for now). The Human-Cognitive-Connections section (§7.8) is the strongest available third-party validation of the project's stated thesis and worth mining directly for the README/research writeup.
