# HippoRAG: Neurobiologically Inspired Long-Term Memory for Large Language Models

- **Authors / venue / year:** Jiménez Gutiérrez, Shu, Gu, Yasunaga, Su — NeurIPS 2024
- **arXiv / DOI:** arXiv:2405.14831v3
- **Source:** folder
- **Overall relevance to longmem-npc:** High — the paper's central mechanism (knowledge-graph + Personalized PageRank multi-hop associative retrieval) is a direct answer to a gap the baseline names explicitly: *"No graph / associative structure over memories (no entity graph, no linking beyond identity-components + gist spans + entities[]). No multi-hop retrieval."*
- **Core contribution (2-3 sentences):** HippoRAG builds a schemaless knowledge graph (KG) from a text corpus via LLM-driven OpenIE (open information extraction into subject-relation-object triples), plus synonym edges from a dense retriever, mimicking the neocortex/hippocampus split. At query time it extracts named entities from the query, links them to KG nodes, and runs Personalized PageRank (PPR) seeded at those nodes to do multi-hop associative retrieval in a single step — no iterative retrieve-then-generate loop needed. It beats standard RAG and iterative methods (IRCoT) on multi-hop QA by up to 20 points while being 10-30x cheaper/faster online.

### Mechanisms relevant to us
- **Offline indexing:** LLM extracts `(subject, relation, object)` triples per passage into a schemaless KG (§2.3, p.4: *"we first use L to extract a set of noun phrase nodes N and relation edges E from each passage in P via OpenIE"*).
- **Synonymy edges:** a retrieval encoder adds edges between distinct-but-similar noun phrases when cosine similarity exceeds a tuned threshold (θ=0.8) — this is how the KG merges near-duplicate entity mentions across passages without a rewrite (§2.3; §3.4 tunes θ on held-out data).
- **Personalized PageRank (PPR) retrieval:** query named entities are linked to KG "query nodes," PPR seeds probability mass only at those nodes, then propagates through the graph; passages are ranked by aggregated node probability over their extracted triples (§2.3, p.4-5).
- **Node specificity:** an IDF-like per-node weight `s_i = |P_i|^-1` (inverse of how many passages a node/entity appears in) multiplies each query node's seed probability before PPR runs — a "rare entity matters more" signal computed with purely local, already-available counts (§2.3, p.5).
- **Incremental, non-destructive graph growth:** new documents just add nodes/edges to the existing KG — no re-summarization or corpus-wide rebuild is needed when new data arrives (§6.1, p.9: *"HippoRAG can continuously integrate new knowledge by simply adding edges to its KG"*, contrasted explicitly against RAPTOR/MemWalker/GraphRAG which must re-summarize).

### NOT-YET-BUILT candidates

- **Capability:** Multi-hop, entity-graph-based associative retrieval as a channel alongside vector similarity search.
- **What the paper does:** Builds a KG of extracted entity/relation triples over the corpus, then answers a query by seeding Personalized PageRank at the query's named entities and reading off which passages accumulate the most graph-propagated probability — this lets one retrieval step surface facts that never co-occur in any single passage/embedding neighborhood (§2.2-2.3; example, p.2: *"Since current methods encode passages in isolation, they would struggle to identify Prof. Thomas unless a passage mentions both characteristics at once"* — HippoRAG gets there via the graph path). Table 6 (2WikiMultiHopQA) shows R@5 improved 20 points over the strongest single-step baseline.
- **Why worth adopting for an NPC memory service:** Our `identity_components` table + `memories.entities`/`memory_fact_versions.entities` are already a proto-graph (canonical entities + aliases), but there is no traversable edge structure and no multi-hop query path — the baseline names this gap outright. An NPC that needs to connect "the blacksmith" to "the guild master's brother" across two unrelated observations (never embedded near each other) is exactly HippoRAG's path-finding case (Table 7, p.8, the "Stanford professor" example is the general form of this). This is a capability, not a scoring tweak — nothing in the read path today does multi-hop entity chaining.
- **Adoption cost/risk in our stack:** Real but bounded. (1) Needs an OpenIE extraction step (LLM call) at write time — a new model role, which is compatible with the "every model role gets its own env var" rule but is genuinely new surface area, not a slot we already reserved. (2) Needs a graph representation + PPR computation — Postgres has no native graph/PPR primitive; this would live app-side (e.g., build a `networkx`/`igraph` graph from `identity_components` + a new triples table, recomputed or incrementally updated per write) since "no ORM/no query builder" is about the relational layer, not a ban on an in-process graph structure. (3) Growth is additive (new nodes/edges only) — this is compatible with the non-destructive invariant; nothing here requires UPDATE-in-place or DELETE. (4) Node specificity's IDF-style weight is cheap (one extra count column) and could enhance the gate's entity tripwire independent of the full PPR machinery, if a smaller pilot is wanted first.
- **Docs it would touch:** `docs\architecture.md` §4.4 (data model — new triples/graph table), `docs\read-path.md` (new retrieval channel alongside vector top-k), possibly a new `docs\graph-retrieval.md` spec if pulled into scope.
- **Confidence:** High (mechanism is precisely specified, ablated, and the gap it fills is explicitly named in our own baseline).

### THESIS-TENSION flags
*(none — the mechanism is purely additive to an existing KG; it neither mutates nor deletes any memory content, and doesn't touch the locked embedding dimension, model roles, or non-LLM-gate invariants)*

### Quotable lines / citations for positioning
- p.2: *"Since current methods encode passages in isolation, they would struggle to identify Prof. Thomas unless a passage mentions both characteristics at once. In contrast, most people familiar with this professor would remember him quickly due to our brain's associative memory capabilities."* — good framing quote for why flat vector retrieval under-serves an NPC's associative recall.
- §6.1, p.9: contrasts HippoRAG's edge-only incremental growth against RAPTOR/GraphRAG's destructive resummarization-on-update — useful supporting citation for our own non-destructive-storage argument (a different mechanism, same underlying principle: don't rewrite what you already stored).

### Verdict
P2 worth-piloting: the KG+PPR associative-retrieval capability directly fills a gap the baseline names, is additive/non-destructive, and has strong, replicated benchmark evidence — but it's a genuinely new subsystem (new model role, new graph structure, new query path) rather than a drop-in improvement, so it should be scoped as its own spec/target rather than folded into an existing build.
