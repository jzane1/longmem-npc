# From Isolated Conversations to Hierarchical Schemas: Dynamic Tree Memory Representation for LLMs (MemTree)

- **Authors / venue / year:** Rezazadeh, Li, Wei, Bao (Accenture) — ICLR 2025
- **arXiv / DOI:** arXiv:2410.14052v3
- **Source:** folder
- **Overall relevance to longmem-npc:** Medium-High — MemTree's central claim is an *online* (no full-corpus-rebuild) hierarchical schema tree that grows as new memories arrive, which speaks directly to a gap the baseline names: *"No hierarchical/schema memory (episodic only; no consolidation into semantic summaries beyond reflection-as-endpoint)."* The mechanism that makes the tree work, however, mutates node content in place — a direct collision with our non-destructive invariant, so this paper carries both a real finding and a real flag.
- **Core contribution (2-3 sentences):** MemTree represents memory as a tree where each node holds aggregated text + an embedding; new information is routed top-down by comparing its embedding against each level's children, either extending an existing branch, creating a sibling leaf, or expanding a leaf into a parent — an O(log N) insertion that updates ancestor summaries as it goes. Retrieval flattens the whole tree ("collapsed tree retrieval") and ranks all nodes at all depths by cosine similarity to the query. It outperforms flat lookup-table memory (MemoryStream, MemGPT) on long multi-session dialogue and multi-hop document QA, and approaches offline hierarchical methods (RAPTOR, GraphRAG) despite updating incrementally instead of rebuilding.

### Mechanisms relevant to us
- **Online hierarchical clustering / schema growth:** each new memory is routed into an existing tree via depth-adaptive cosine-similarity comparison against sibling nodes at each level; insertion is O(log N) and requires no rebuild of prior structure (§3.1, p.4: *"MemTree dynamically adapts by traversing the existing structure, identifying the appropriate subtree for integration, and updating relevant nodes"*).
- **Depth-adaptive similarity threshold:** `τ(d) = τ₀ · e^(αd)` — deeper (more specific) nodes require higher similarity to accept new content, which is how the tree keeps abstraction levels coherent as it grows (§3.1, p.4).
- **Ancestor aggregation on insert:** every ancestor along the insertion path gets its content and embedding updated via an LLM aggregation call conditioned on branching factor `n` — this is literally how the tree "learns" higher-level schemas from accumulating detail (§3.1, p.4-5: *"cv ← Aggregate(cv, cnew | n)"*).
- **Collapsed tree retrieval:** at read time the tree is treated as one flat set of embedded nodes across all depths; cosine similarity to the query is computed for all of them, low scorers are filtered, and top-k wins (§3.2, p.5) — this is retrieval-cost-neutral versus a flat lookup table (same vector-search shape), the tree structure only changes what gets *written*, not how it's *searched*.
- **Explicit contrast with offline consolidation methods:** RAPTOR and GraphRAG require full corpus reconstruction to add new information and "do not support online memory updates" (§2, p.3) — MemTree's selling point is exactly the incremental-update property our own system would need if it ever grew a consolidation layer.

### NOT-YET-BUILT candidates

- **Capability:** Incremental, online hierarchical schema-tree memory consolidation — organizing episodic memories into a growing tree of increasingly abstract summaries, built up one insertion at a time rather than via a periodic offline batch job.
- **What the paper does:** Grows a tree top-down as each new memory arrives, aggregating ancestor content along the way, and shows this matches or beats offline hierarchical methods (RAPTOR, GraphRAG) on multi-document QA while inserting in ~10 seconds vs. over an hour for a full RAPTOR/GraphRAG rebuild (§5.3, Fig. 5, p.10: *"MemTree inserts new information in 10 seconds on average, while RAPTOR and GraphRAG take over an hour to build the full memory tree"*).
- **Why worth adopting for an NPC memory service:** Our baseline's reflection pipeline is designed as a post-August, non-scheduled endpoint that samples episodes by importance×recency but has no hierarchical structure — it produces a flat identity revision, not a tree of intermediate abstractions. MemTree's core idea (organize memories into a schema hierarchy *as they're written*, not in a big batch pass) is a genuinely new consolidation shape that could inform how reflection eventually structures the identity-components table or a future semantic-summary layer, without requiring a scheduled batch job.
- **Adoption cost/risk in our stack:** Real, and it's the mechanism itself that's the risk, not just the infra: MemTree's node update literally overwrites `cv` (the parent's stored text) with a new LLM-generated aggregate every time a descendant is added — see the THESIS-TENSION flag below. A workable adaptation for us would need to version each tree node's aggregate as a new bi-temporal row (append + supersede via `invalid_at`, matching our `memory_details`/`memory_fact_versions` pattern) rather than mutate node content in place; that changes the mechanism from an O(log N) *update* to an O(log N) *insert-and-supersede*, which is a design change the paper doesn't need to make (it has no non-destructive constraint) but we would.
- **Docs it would touch:** would most naturally land in the still-undesigned reflection/consolidation mechanism — `docs\architecture.md` (reflection §, currently mechanism-post-August), a future `docs\reflection.md` spec.
- **Confidence:** Medium — the online-insertion property and its efficiency case are well-evidenced (Fig. 5, Table 5), but the paper's evaluation is all general-purpose dialogue/document QA, not NPC memory specifically, and adopting it for us requires the non-destructive re-engineering noted above, which is untested territory.

### THESIS-TENSION flags

- **Invariant challenged:** #1, Bi-temporal, non-destructive storage (*"Supersede by stamping `invalid_at`; never UPDATE stored content in place; never DELETE"*).
- **What the paper does that conflicts:** The core update rule is `cv ← Aggregate(cv, cnew | n)` — the parent node's stored text is literally replaced by a new LLM-generated aggregate every time a new leaf is inserted beneath it (§3.1, p.4-5). Older phrasings of the aggregate are not retained anywhere; only the latest aggregate survives at each node. This is the same "destructive summarization" pattern the baseline explicitly calls out as a tension for Mem0/MemoryBank/MemGPT-style eviction.
- **Honest read:** This is a genuine tension, not an apples-to-oranges mismatch — MemTree is trying to solve exactly the problem our reflection/consolidation gap names (turning accumulating episodes into higher-level schema), so the collision is real and worth Jack seeing rather than silently dropping the paper. The fix is architecturally straightforward (version node aggregates instead of overwriting them) but is *our* adaptation to make, not something the paper offers — flagging honestly that "hierarchical online consolidation" is adoptable in spirit but the literal algorithm as published is not drop-in compatible with the non-destructive invariant.

### Quotable lines / citations for positioning
- §2, p.3: *"these methods [RAPTOR, GraphRAG] are limited to static corpora, requiring full reconstruction to integrate new information, and do not support online memory updates"* — useful contrast citation for why an always-on NPC memory service needs an incremental (not batch-rebuilt) consolidation story if it ever grows one.
- §1, p.1: MemTree is explicitly framed against human "schemas" (Anderson 2005; Gilboa & Marlatte 2017) — same cognitive-science register as our own identity-conditioned reconstruction framing, useful shared vocabulary for a related-work section.

### Verdict
P3 note-only: the online-incremental-consolidation *idea* is the right shape for our still-undesigned reflection pipeline and worth remembering when that spec is written, but the published mechanism's in-place node overwriting is a direct non-destructive-storage conflict that would need real re-engineering (versioned tree nodes) before anything here could be built as-is — not a near-term pilot candidate.
